# Testing the StaySphere API with Postman

This is the document to follow when you need to satisfy yourself that the backend
actually works — not that it compiles, not that its unit tests pass, but that a
guest can book a room, pay for it, check in, run up a bar tab, check out, and be
invoiced, and that a housekeeper cannot read the audit log while doing it.

Everything here runs against the **gateway**, on `http://localhost:3000`. That is
deliberate. Hitting a service directly on its own port skips edge authentication,
and a suite that skips the edge will happily pass while the front door is wide
open. If it does not work through the gateway, it does not work.

## What you get

Three files in [`postman/`](../postman), all generated by
[`scripts/build-postman.mjs`](../scripts/build-postman.mjs):

| File                                           | What it is                                                                               |
| ---------------------------------------------- | ---------------------------------------------------------------------------------------- |
| `StaySphere.postman_collection.json`           | The verification suite. 185 requests, 415 assertions, 16 folders, run in order.          |
| `StaySphere.reference.postman_collection.json` | All 95 endpoints grouped by service, with no assertions — for poking at the API by hand. |
| `StaySphere.local.postman_environment.json`    | `baseUrl`, the seeded accounts and their password. Nothing else.                         |

The suite is generated rather than hand-written, but only the _inventory_ is
generated: the route table and the authorization matrix are read out of the
controllers so they cannot drift from what the services serve. The flows and
their assertions are written deliberately, because a mechanically generated
request per route proves only that a URL exists. What is worth testing is the
sequence — book, pay, check in, check out — and the boundaries between roles.

## Before you start

You need the stack running and the databases seeded. In full, from a clean
checkout:

```bash
pnpm install
pnpm setup:local          # creates the 14 databases and writes each service's .env
pnpm db:migrate
pnpm db:seed              # one property, its rooms and rates, and one account per role
pnpm dev                  # 15 services + 3 front-ends, in watch mode
```

`pnpm dev` starts eighteen watch processes and wants roughly 4–6 GB of free
memory. If your machine is tight — and this is worth knowing, because the
symptom is a wave of `503 UPSTREAM_UNAVAILABLE` responses halfway through a run
rather than an obvious crash — build once and run the compiled output instead:

```bash
pnpm build
pnpm dev --filter='./services/*'   # backend only, no Next.js dev servers
```

Then confirm the platform is actually up before you blame the tests:

```bash
curl -s localhost:3000/ready | jq
```

You want `"status": "ok"` and **fourteen** entries under `checks`. Anything less
means a service is down, and the folders that depend on it will fail for reasons
that have nothing to do with your change.

## Import and run

1. **Import both collections and the environment.** Postman → Import → drag in
   all three files from `postman/`.
2. **Select the environment** — "StaySphere — local" — in the top-right picker.
3. **Run the collection**: right-click _StaySphere API_ → _Run collection_.
4. **Set the delay to 650 ms** in the runner options. This matters; see below.
5. Press _Run_. It takes about five minutes and should end with **0 failed** on
   both counters — assertions _and_ test-scripts. A failed test-script is not a
   failed assertion: it means a check never ran at all, while the summary still
   reads zero assertion failures.

> **Why the delay?**
> The gateway rate-limits each client to 120 requests a minute. The suite makes 185. Without a delay you will get a wall of `429`s from about request 120
> onwards, the logins will fail, and every subsequent assertion will fail for
> want of a token. 650 ms keeps the suite at roughly 90 requests a minute, which
> is comfortably inside the limit. This is the rate limiter working, not a bug.

### Run the folders in order

Later folders reuse what earlier ones capture. Folder 05 checks in the booking
that folder 03 created; folder 08 reviews the stay that folder 05 closed. Running
folder 05 on its own will fail for want of a booking id — that is expected, not a
broken test. If you want to run one folder, run 01 first to get tokens.

Folder 15 is last on purpose: it deliberately exhausts the rate-limit budget for
one path, and that path stays exhausted for the remainder of the minute.

## Running it from the command line

The same collection runs headless, which is what you want in CI or when you are
iterating:

```bash
pnpm postman:run
```

That is `newman` with the environment and the delay already set. Useful
variations:

```bash
# One folder
pnpm exec newman run postman/StaySphere.postman_collection.json \
  -e postman/StaySphere.local.postman_environment.json \
  --folder "03 · The booking path"

# Against a deployed environment
pnpm exec newman run postman/StaySphere.postman_collection.json \
  --env-var baseUrl=https://api.staging.staysphere.example/api/v1 \
  --env-var host=https://api.staging.staysphere.example \
  --env-var password="$STAYSPHERE_TEST_PASSWORD" \
  --delay-request 650

# An HTML report
pnpm exec newman run postman/StaySphere.postman_collection.json \
  -e postman/StaySphere.local.postman_environment.json \
  --delay-request 650 -r cli,html --reporter-html-export report.html
```

Newman exits non-zero on any failed assertion, so it drops straight into a CI
step. Do not point it at production: the suite writes bookings, payments, stays,
invoices and reviews.

## What each folder proves

The counts below are requests / assertions.

### `00 · Health and readiness` — 4 / 5

The probe paths Kubernetes and Prometheus use. They answer without a token and
without the `/api/v1` prefix, because a probe that needs either fails in
production while every service is perfectly healthy.

- `/health` and `/ready` return a flat document, not the API envelope — that is
  what a probe consumer expects.
- `/ready` names **all fourteen** upstreams. The assertion is on the count, not
  just on the statuses: a readiness probe that checks eight of fourteen reports
  ready while six services are down.
- `/metrics` serves Prometheus text without a token.
- An unrouted path is a clean `404` in the standard envelope, not an HTML error
  page.

### `01 · Authentication` — 13 / 22

Signs in as all seven roles and stores each token. Everything downstream depends
on this folder.

- A token pair comes back with `tokenType: "Bearer"`.
- `/auth/me` returns the principal and **never** the password hash.
- A wrong password and an unknown email return **byte-identical** responses —
  same status, same code, same message. Anything else is an account-enumeration
  oracle: an attacker learns which of your guests' email addresses are
  registered.
- A weak password is refused at registration.
- No token gives `401 UNAUTHENTICATED`; a malformed token gives the same, not a 500.

### `02 · Property, rooms and rates` — 6 / 10

What a guest may browse without signing in, and what only staff may see.

- The public property list contains only `ACTIVE` properties.
- The property's own policy has check-out **before** check-in, which is what
  makes same-day turnover sellable.
- The floor board is staff-only and every room carries a written status, not
  only a colour.
- A nearly sold-out night prices above the base rate, and every amount is a whole
  number of minor units.

### `03 · The booking path` — 9 / 14

The path that earns the money. Everything else can degrade for a day; if this
breaks, the business stops.

- Availability returns an itemised quote: one line per night, and
  `total = subtotal − discount + tax`.
- Tax is charged on the **discounted** amount, not the gross.
- The booking reference matches `SS-` plus six characters drawn from an alphabet
  with `0 O 1 I L S B` removed, because references get read down a telephone.
- Replaying the same `Idempotency-Key` returns `409 IDEMPOTENCY_KEY_REUSED`
  naming the original reference — it does not create a second booking. This is
  the assertion that stops a guest being charged twice for one impatient click.
- Inventory drops by **exactly one**.
- An inverted range and a zero-night range are both `400 INVALID_DATE_RANGE`,
  which is how you know the half-open interval `[checkIn, checkOut)` is checked
  at the boundary and not merely near it.
- Reading the booking back: the nightly charges sum to the subtotal.

### `04 · Payments and refunds` — 7 / 9

Where getting it wrong costs real money.

- A payment captures in full and the response contains no card data — no `pan`,
  no `cvv`, no `cardNumber` — under any key.
- Replaying the payment key returns the original charge, not a second one.
- **Refunding more than was captured is refused**, and the error states what is
  actually available.
- After a partial refund, a second refund is capped at
  `captured − alreadyRefunded`. The assertion checks that arithmetic against the
  numbers in the error body rather than trusting a status code.
- A guest cannot issue a refund on their own booking.

### `05 · Check-in, folio and check-out` — 9 / 10

- Checking the same reservation in twice is a `409` naming the existing stay.
- A manual charge's line total is `quantity × unitPrice`.
- The folio is **append-only**: posting a charge adds a line, it does not amend
  the room charge. Both lines are still there afterwards.
- Check-out with an unsettled folio is refused, and the error states the exact
  balance due.
- Settling and departing leaves `balanceDue = 0` and removes the guest from the
  in-house register.

### `06 · Housekeeping` — 13 / 14

- A room with a guest arriving within the hour is `CRITICAL`; a deep clean with
  nobody arriving is `LOW` — **regardless of which was queued first**. The board
  is then checked to confirm the urgent room genuinely sorts above the quiet one.
- A housekeeper cannot start a task assigned to somebody else.
- Completing with the checklist untouched is a `409` naming every outstanding
  required item. The checklist is what turns "the room looks done" into "the room
  was done".
- A **failed inspection reopens the task** as `CRITICAL` rework with the
  checklist cleared. It does not close it, and it does not let a re-tick stand in
  for a re-clean.
- Rostering a shift is `staff:manage`, which housekeeping does not hold.

### `07 · Maintenance` — 11 / 14

- A major plumbing fault in an **occupied** room reported as `MEDIUM` is
  escalated to `CRITICAL` and takes the room out of sale. The reporter's own
  assessment is a floor, never a ceiling — the guest is in the room now.
- The SLA deadline is two hours out for `CRITICAL`, derived from the response
  rather than hard-coded.
- A cosmetic fault in an empty room stays `LOW` and the room stays sellable.
- Closing before resolving is a `409` that lists the transitions that _are_
  allowed.
- The summary counts only open work.

### `08 · Reviews and moderation` — 13 / 17

The moderation bias is the point: **flag for a human, do not auto-reject.**

- A clean review publishes immediately, with `moderation.flags` empty.
- The overall score is the unweighted mean of the category scores, to one
  decimal. Unweighted is deliberate — weighting lets a property game its headline
  score by optimising whichever category carried the most weight.
- The same stay cannot be reviewed twice.
- A review carrying an email address is `REJECTED` with the reason stated: it
  cannot be published as written.
- A terse, critical review is `PENDING_MODERATION`, **not** rejected. The
  assertion explicitly checks it was not flagged as profanity. Silently dropping
  criticism is dishonest and, in most jurisdictions, unlawful.
- The public list shows published reviews only; the author still sees their own
  rejected one.
- A guest cannot open the moderation queue or reply on behalf of the hotel.

### `09 · Invoicing` — 12 / 16

- The invoice number is `PREFIX-YEAR-NNNNNN` and the second invoice takes the
  **next** number in the sequence.
- Subtotal is the sum of the lines; tax is itemised (`VAT`, `CITY`) and the
  components add up to the tax total; `total = subtotal − discount + tax`.
- Overpaying is refused, and the error states what is outstanding.
- A part-paid invoice **cannot** be voided — refund first.
- Voiding keeps the row and the number. Deleting it would leave a gap in a
  sequence that most tax authorities require to be gap-free.
- A receptionist cannot void an invoice.
- Period revenue reconciles and excludes voided invoices.

### `10 · Notifications` — 13 / 14

- A template may not declare a required token that its body does not contain.
- **Replaying the same `eventId` queues nothing.** Delivery is at-least-once, so
  the same domain event must never produce two messages to the guest.
- Reading somebody else's notification returns `404`, not `403` — a `403` would
  confirm the id exists.
- Marking a message read twice keeps the original timestamp.
- A guest cannot send notifications or publish templates.

### `11 · Reporting` — 10 / 13

The KPI arithmetic, checked against the figures fed in one request earlier.

- Occupancy is `roomsSold ÷ roomsAvailable`; ADR is `roomRevenue ÷ roomsSold`;
  RevPAR is `roomRevenue ÷ roomsAvailable`, cross-checked against
  `ADR × occupancy`.
- Total revenue includes services; room revenue does not; neither includes tax.
- An inverted period and a malformed date are both `400`.
- Housekeeping throughput carries a rework rate, so the report cannot be read as
  a pure speed contest.
- Writing the daily figures is `system:admin`; a manager gets `403`.

### `12 · Audit trail` — 7 / 12

The audit log is widely readable by design — that is what oversight means — which
is exactly why nothing sensitive may reach it.

- A change containing a password is recorded with the field **present but
  `[REDACTED]`**. The assertion searches the whole response body for the
  plaintext and requires it to be absent.
- Non-sensitive changes are recorded in full, so the log stays useful.
- One `X-Correlation-Id` reconstructs every entry from a single interaction
  across services — the view you want during an incident.
- History for one record comes back oldest-first.
- `audit:read` is admin-only: a manager gets `403`.

### `13 · Authorization matrix` — 44 / 44

**Generated from the controllers.** Every protected `GET` without a path
parameter is probed twice: once with no token, once with a guest token that lacks
the permission.

This is the folder that catches a guard which was declared but never registered —
the failure where a green unit-test suite and an unprotected endpoint coexist
happily, because `@RequirePermissions` is only a decorator until something reads
it. It is generated so that adding a service without wiring its guard fails here
automatically, without anyone remembering to write a test.

### `14 · Error handling and envelopes` — 8 / 9

- One response shape whatever goes wrong: `success: false`, `error.code`,
  `error.message`, `requestId`.
- A `404` never leaks a stack trace, a file path or a `node_modules` reference.
- Every response carries `x-request-id`, and the header matches the `requestId`
  in the body — that is what makes a user's screenshot traceable to a log line.
- A caller-supplied `X-Correlation-Id` survives the hop to the upstream.
- **A forged `x-staysphere-*` principal header is ignored.** Those headers are
  how the gateway tells services who the caller is; if an inbound copy were
  trusted, anyone could claim to be `SUPER_ADMIN` with a `curl` one-liner. The
  test sends exactly that and requires a `401`.
- The usual hardening headers are set at the edge.

### `15 · Rate limiting` — 6 / 7

Trips the tightest credential limit deliberately and requires `429 RATE_LIMITED`
with the limit and a retry hint in the body — then confirms a different endpoint
still answers `200`, because the counter is keyed per route and exhausting one
path must not take the API down with it.

## Writing your own requests

A few things will bite you.

**Numbers in a JSON body.** Postman substitutes variables textually, so
`"amountMinor": "{{bookingTotal}}"` sends the **string** `"34043"` and every
integer schema rejects it with a `400`. Leave the quotes off:

```json
{ "amountMinor": {{bookingTotal}} }
```

**Environment variables outrank collection variables.** If a name exists in both
scopes, the environment wins. That is why the environment file holds only
configuration — `baseUrl`, emails, password — and never the runtime values. An
empty `guestToken` in the environment would shadow the one the login test just
captured, and every authenticated request would go out unauthenticated, giving
you a folder full of `401`s and no obvious cause.

**`roomTypeId` is the type code, not the row id.** Booking and pricing identify a
room type by its code — `DELUXE`, `DOUBLE`, `SUITE`, `FAMILY` — because those
services own separate databases and never see room-service's primary keys.
`GET /rooms/types` returns the room-service records, whose `code` field is what
you pass to `/bookings/availability` and `/rates/quote`.

**Dates.** `checkIn` and `checkOut` are `YYYY-MM-DD` and the interval is
half-open: `[checkIn, checkOut)`. A stay ending on the 12th does not conflict with
one starting on the 12th. Reporting periods use `YYYY-MM-DD`; invoice and audit
filters use full ISO-8601 timestamps.

**Idempotency.** `POST /bookings`, `POST /payments` and `POST /payments/:id/refund`
take an `Idempotency-Key` header. Reuse it and you get the original result or a
`409`; never a duplicate. Use a fresh key per logical operation — the collection
generates one per run.

**Money is always integer minor units.** `34043` is $340.43. There are no floats
anywhere in the API.

## Checks that are not in the collection

Some things are worth knowing but do not belong in an automated suite.

**Load.** Assertions on `responseTime` are a hang detector, not a latency budget —
the collection's is set at thirty seconds, and deliberately so; see
[Latency and the hosted database](#latency-and-the-hosted-database). Measure
performance with `k6` or `autocannon` against a build that is not in watch mode.

**Concurrency.** The overlap constraint that prevents double-booking is a
PostgreSQL `EXCLUDE USING gist` constraint, and Postman sends requests in series,
so the suite cannot exercise it. To see it work, fire two overlapping bookings for
the same room at once:

```bash
seq 2 | xargs -P2 -I{} curl -s -X POST localhost:3000/api/v1/bookings \
  -H "authorization: Bearer $TOKEN" -H 'content-type: application/json' \
  -H "idempotency-key: race-{}" \
  -d '{"hotelId":"...","roomTypeId":"DELUXE","checkIn":"2027-03-01","checkOut":"2027-03-04","adults":2,"guestName":"Race","guestEmail":"guest@example.com"}'
```

Exactly one should succeed.

**Real-time.** The gateway serves Socket.IO on the same port with per-property
channel scoping. Postman cannot subscribe; use `wscat` or the staff console.

**Token expiry.** Access tokens outlive a five-minute run, so the suite never
exercises `/auth/refresh` or `TOKEN_EXPIRED`. Test those by hand with a token you
have let go stale.

## Latency and the hosted database

Worth understanding before you read a slow response as a broken one.

The local stack points at Neon in `us-east-1`. From most of the world that is
roughly **300 ms per round trip**, and Prisma issues one round trip per statement.
A write that touches several tables therefore costs seconds, not milliseconds:

```
$ node -e '…SELECT 1 against the configured DATABASE_URL…'
connect    2939 ms
SELECT 1    360 ms
SELECT 1    337 ms
SELECT 1    327 ms
txn(3 RT)   991 ms
```

`POST /invoices` writes a counter row, the invoice, its lines, its tax lines and
an outbox event, then re-reads the lot for the response — around thirty
statements, so **nine to ten seconds** end to end. That is not a hang; it is
thirty round trips across an ocean.

Two settings follow from this, both applied to local development only:

| Setting                                | Local   | Why not everywhere                                                                     |
| -------------------------------------- | ------- | -------------------------------------------------------------------------------------- |
| `UPSTREAM_TIMEOUT_MS` (gateway)        | `30000` | The 10 s default is right when the database is in the same region as the services.     |
| `PRISMA_TX_TIMEOUT_MS` (every service) | `20000` | Prisma's 5 s default aborts an ordinary transaction with `P2028` once latency is real. |

**The failure mode this prevents is worse than slowness.** When the gateway's
timeout fires, it returns `504` to the caller — but the upstream keeps going and
commits. The client sees a failure for an operation that succeeded. If it then
retries, and the endpoint has no `Idempotency-Key` support (`POST /invoices` does
not; `POST /bookings` and `POST /payments` do), it creates a duplicate. If you
are deploying this platform, put the database in the same region as the services,
and treat any endpoint whose p99 approaches the edge timeout as a bug rather than
as a tuning problem.

## What writing this suite found

The suite was not written against a working system and then declared green. It
found five defects, four of which are fixed in the same change as this document.
They are listed because the shape of them is the useful part: every one passed
lint, typecheck, and 519 unit tests.

| What                                                         | Why it mattered                                                                                                                                                                                                     | Status                                                                                                      |
| ------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| `GET /rooms/types` returned one **room**, not the room types | The public browse endpoint on the booking page. It called `list({ pageSize: 1 })`.                                                                                                                                  | Fixed — `listRoomTypes()`, with sellable-room counts                                                        |
| Per-route rate limits were declared but never enforced       | `ROUTE_TABLE` set `/auth/login` to 10/min and `/auth/password-reset` to 5/min. Nothing read the field, so the flat 120/min applied. A limit nothing reads is worse than no limit: it reads as protection in review. | Fixed — `RouteRateLimitGuard`, proven by folder 15                                                          |
| Readiness probed 8 of 14 upstreams                           | The gateway reported ready with six services down, so Kubernetes kept routing to it.                                                                                                                                | Fixed — all fourteen, asserted on the count in folder 00                                                    |
| Prisma's 5 s transaction default                             | `P2028` — a 500 — on payments, folio, invoicing and housekeeping, but only against a database that is not on the same host. Invisible locally, guaranteed in production.                                            | Fixed — shared 20 s budget, and housekeeping's per-item checklist loop replaced with two `updateMany` calls |
| `/auth/password-reset` is routed but has no handler          | The gateway proxies it; the auth service 404s. Dead routing config.                                                                                                                                                 | **Not fixed** — flagged rather than inventing a password-reset feature                                      |

The one that is worth dwelling on is the second. The route table said the login
endpoint was rate-limited, a unit test asserted the declared figure, and code
review would have seen both. Nothing anywhere connected the number to a request.
That is the class of bug a suite like this exists to find: it is invisible to
every check that reads the code, and obvious to the first one that sends a
request.

## When something fails

Work down this list before you suspect the assertion.

| Symptom                                                           | Almost always                                                                                                                                                |
| ----------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Everything after folder 01 is `401`                               | The environment file has runtime variables in it, shadowing the collection variables. It should contain only `baseUrl`, `host`, the emails and the password. |
| A wall of `429` from request ~120                                 | No delay set. Use `--delay-request 650`, or the runner's delay field.                                                                                        |
| `503 UPSTREAM_UNAVAILABLE` partway through                        | A service died — usually memory. Check `curl -s localhost:3000/ready` and count the `up` entries.                                                            |
| `400` on a body that looks right                                  | A `{{variable}}` in a numeric field is quoted, so it arrived as a string.                                                                                    |
| `404` on `/hotels/by-slug/`                                       | The slug variable is empty; the path then matches `/hotels/:id` upstream, which is staff-only. Check that folder 02's first request ran.                     |
| `500` with `P2028` in the service log                             | An interactive transaction timed out. `PRISMA_TX_TIMEOUT_MS` (default 20 s) is the knob; a transaction that needs more is doing too many round trips.        |
| One folder fails in isolation but passes in a full run            | Expected. Folders share state by design. Run 01 first.                                                                                                       |
| Newman says `test-scripts … 1 failed` but `assertions … 0 failed` | A script did not parse, so its check never ran. `pnpm postman:build` refuses to write a collection containing one, so this means the JSON was hand-edited.   |
| `504 UPSTREAM_TIMEOUT` on a write                                 | The gateway gave up before the upstream finished committing. See [Latency and the hosted database](#latency-and-the-hosted-database).                        |
| `P1001 Can't reach database server` in a service log              | The link to the database dropped, usually because the machine was saturated by something else. Re-run with nothing competing.                                |

Every failure response carries a `requestId`, and it is echoed in the
`x-request-id` header. Grep the service logs for it and you will get the whole
request, including which guard rejected it:

```bash
grep req_XXXXXXXXXXXXXXXX services/*/logs/*.log
```

## Regenerating the collection

```bash
pnpm postman:build
```

Reads every `*.controller.ts` under `services/`, rebuilds the route table, the
authorization matrix and the reference collection, and rewrites all three JSON
files. Run it after adding or changing an endpoint, and commit the result — the
generated files are checked in so that importing into Postman needs no build step.

The flows in folders 00–12, 14 and 15 are hand-written in
[`scripts/build-postman.mjs`](../scripts/build-postman.mjs); folder 13 and the
reference collection are derived. If you add an endpoint and folder 13 grows by
two requests on the next build, that is the matrix doing its job.

The build parses every test script before it writes anything and refuses to
produce a collection containing one that does not compile. It also runs Prettier
over what it writes, so `pnpm format:check` passes on a clean build.
